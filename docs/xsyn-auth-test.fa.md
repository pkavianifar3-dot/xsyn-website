# راهنمای ورود آزمایشی XSYN

فقط برای مخزن xsyn-website و پروژه **xsyn-platform-test** با ref **awfnvhlytiwckkkwfgbc**. هیچ SQL را در پروژه دیگری اجرا نکنید.

## وضعیت و فایل‌ها

مسیر پیشنهادی پس از انتشار: https://xsynplatform.ir/auth-test/
منوها، مسیرها و محتوای عمومی فعلی تغییر نکرده‌اند. با اجازهٔ کاربر، Publishable key همین پروژه وارد شده است. Migration 001، آزمون تراکنشی 003 و هر دو قالب فارسی ایمیل در Supabase اجرا و ذخیره شدند. ثبت‌نام و ورود ایمیلی دو حساب واقعی آزمایش شد. DNS تغییر نکرده است. کاربر commit و push فقط فایل‌های این قابلیت را تأیید کرده؛ وضعیت انتشار از این راهنمای ثابت قابل استنتاج نیست و باید روی دامنه بررسی شود. جزئیات و محدودیت‌ها در [گزارش آزمون](./xsyn-auth-test-results.fa.md) آمده است.

## اجرای محلی بدون نصب بسته

از ریشه پروژه با Node موجود:

```powershell
node --test tests/auth/core.test.mjs
node tests/auth/serve.mjs --port=8788
```

http://127.0.0.1:8788/auth-test/ را باز کنید؛ ماژول‌ها با file:// اجرا نمی‌شوند. کلید عمومی اکنون وارد شده و پیش‌نمایش عادی به پروژهٔ واقعی متصل است؛ اجرای --mock برای آزمون بدون ایمیل است. با placeholder کلاینت ساخته نمی‌شود. توقف با Ctrl+C است.

آزمون کاملاً ساختگی، بدون ارسال ایمیل یا درخواست Supabase:

```powershell
node tests/auth/serve.mjs --mock --port=8789
```

در http://127.0.0.1:8789/auth-test/ ثبت‌نام new@example.test و ورود حساب قبلی member@example.test است. کد ساختگی 12345678 یا ۱۲۳۴۵۶۷۸ و ایمیل خطای شبکه network@example.test است. پاسخ config و SDK فقط در حافظه سرور جایگزین می‌شود؛ فایل اصلی تغییر نمی‌کند. نشان شبیه‌سازی روی صفحه است؛ این حالت اثبات SMTP، JWT یا RLS نیست. نشست ساختگی با خروج حذف می‌شود؛ پروفایل mock پس از reload بازنشانی می‌شود.

سرور فقط روی 127.0.0.1 و GET/HEAD است؛ ابزار انتشار نیست.

## تنظیم داشبورد پس از تأیید

1. نام **xsyn-platform-test** و ref **awfnvhlytiwckkkwfgbc** را بررسی کنید.
2. Publishable key همین پروژه با اجازهٔ کاربر در auth-test/config.js قرار گرفته است. فقط کلید عمومی با پیشوند sb_publishable_ مجاز است؛ نام و URL را تغییر ندهید.
3. secret، service_role، JWT کلید قدیمی anon، رمز دیتابیس یا کلید Resend وارد کد نشود. کد فقط شکل publishable را می‌پذیرد؛ این کلید مجوز عبور از RLS نیست.
4. Email login، ثبت‌نام و Confirm email فعال؛ اعتبار OTP برابر 600 ثانیه و طول کد هشت رقم باشد.
5. SMTP Resend با فرستنده noreply@auth.xsynplatform.ir بررسی شود. مرورگر مستقیماً Resend را فراخوانی نمی‌کند.
6. محدودیت درخواست و تأیید در Auth سمت سرویس لازم است. تایمر 60 ثانیه‌ای رابط قابل دورزدن است و جای محدودیت سرور را نمی‌گیرد.
7. Site URL همان https://xsynplatform.ir باشد. **این جریان عددی Redirect URLs لازم ندارد؛ خالی ماندن آن درست است.** کد emailRedirectTo ندارد و detectSessionInUrl خاموش است. برای OAuth یا لینک آینده، allowlist دقیق جدا لازم است؛ اکنون wildcard اضافه نکنید.
8. دامنه اصلی را برای ورود استفاده کنید؛ www و pages.dev مبدأ و نشست جدا دارند. این تغییر ریدایرکت دامنه ایجاد نمی‌کند.

### هر دو قالب ایمیل لازم‌اند

Magic Link برای حساب موجود و **Confirm signup برای حساب جدید** باید Token را نمایش دهند. تغییر فقط Magic Link کافی نیست. نمونه:

```html
<div dir="rtl" lang="fa">
  <h2>کد ورود XSYN</h2>
  <p>کد هشت‌رقمی شما:</p>
  <p dir="ltr" style="font-size:28px;letter-spacing:6px">{{ .Token }}</p>
  <p>کد تا ۱۰ دقیقه معتبر است. اگر درخواست از شما نبود، پیام را نادیده بگیرید.</p>
</div>
```

موضوع Confirm signup «کد تأیید حساب XSYN» و Magic Link «کد ورود XSYN» باشد. لینک ConfirmationURL لازم نیست. هر دو قالب با تأیید کاربر ذخیره و ارسال واقعی هر دو جریان آزمایش شده‌اند. نسخهٔ کامل HTML در email-templates نگهداری می‌شود.

هر دو جریان verifyOtp با type:email دارند. ورود shouldCreateUser:false و ثبت‌نام true است. ثبت‌نام ایمیل موجود ممکن است از طرف سرویس به ورود تبدیل شود؛ رابط وجود حساب یک ایمیل را قطعی اعلام نمی‌کند.

Cloudflare Email Routing فقط دریافت است. هیچ MX، SPF، DKIM، DMARC یا DNS تغییر نکرده است. SMTP واقعی با تحویل دو ایمیل و لاگ Auth/Resend بررسی شود؛ کد و کلید در گزارش نوشته نشود.

## داده‌ها و مرز دسترسی

| داده | محل | دسترسی |
| --- | --- | --- |
| ایمیل و احراز هویت | auth.users | در پروفایل کپی نمی‌شود؛ UI فقط ایمیل صاحب نشست را نشان می‌دهد |
| UUID، نام و معرفی | xsyn_profiles | پیش‌فرض مخفی؛ با is_listed=true برای همه قابل خواندن |
| وضعیت انتشار و زمان‌ها | xsyn_profiles | جزو سطر قابل خواندن؛ زمان‌ها فقط سرور تعیین می‌کند |
| یادداشت خصوصی آزمایشی | xsyn_profile_private | فقط صاحب حساب می‌خواند و private_note را تغییر می‌دهد |
| شناسه طرفین و زمان رابطه | xsyn_follows | فقط دنبال‌کننده می‌خواند/ایجاد/حذف می‌کند؛ دنبال‌شونده نمی‌بیند |
| نشست | localStorage با نام مخصوص پروژه | همان مبدأ/مرورگر؛ ایمیل درخواست یا OTP برای تایمر ذخیره نمی‌شود |

فهرست فقط 30 پروفایل جدید منتشرشده را نمایش می‌دهد؛ جست‌وجو/صفحه‌بندی و شمارنده عمومی ندارد. مخفی‌کردن پروفایل مانع خواندن بعدی و دنبال‌کردن جدید است. رابطه قبلی خصوصی می‌ماند و قابل لغو است؛ UUID هدف قبلی نزد دنبال‌کننده معلوم می‌ماند.

شناسه، نقش و زمان از UI قابل تغییر نیست. follower_id باید auth.uid() باشد؛ تکرار و خوددنبال‌کردن ممنوع‌اند. تریگر از auth.users.id استفاده می‌کند و به metadata قابل تغییر کاربر اعتماد نمی‌کند. پروفایل هنگام ثبت Auth، حتی پیش از تأیید ایمیل، مخفی ساخته می‌شود. مدیر دیتابیس و service_role از RLS عبور می‌کنند و در مرورگر مجاز نیستند.

اطلاعات حساس یا ایمیل در نام/معرفی قابل انتشار نوشته نشود. noindex و نداشتن لینک منو صفحه را خصوصی نمی‌کند. محتوای منتشرشده قابل کپی است.

### نصب SQL، فقط بعد از تأیید

نام/ref را دوباره بررسی، وضعیت را پشتیبان‌گیری و 001 را کامل مرور کنید. SQL Editor تضمین خودکار تطبیق نام پروژه ندارد. فایل 001 قبلاً در همین پروژه اجرا شده است؛ دوباره اجرا نکنید. برای نصب تازه، یکجا اجرا می‌شود، مخصوص بار اول و اتمیک است و تداخل نام باید خطا بدهد. پروفایل کاربران فعلی همین پروژه نیز با انتشار خاموش ساخته می‌شود. xsyn_internal را در Data API expose نکنید.

بدون SQL ورود ممکن است موفق شود ولی بخش داده غیرفعال و خطادار بماند؛ این وضعیت تأیید RLS نیست.

## ماتریس آزمون واقعی

دو ایمیل تحت کنترل خودتان و دو فضای ذخیره‌سازی مستقل A و B لازم است؛ دو tab عادی یک مبدأ نشست مشترک دارند. در آزمون واقعی این تحویل، دو مبدأ loopback با پورت متفاوت به همان Supabase متصل بودند؛ این شیوهٔ جداسازی آزمون محلی است، نه تنظیم دامنهٔ انتشار.

| آزمون | نتیجه لازم |
| --- | --- |
| صفحه اصلی/صنایع بدون نشست | بدون اجبار ورود یا تغییر مسیر |
| ثبت‌نام A جدید | دریافت واقعی Confirm signup با کد هشت‌رقمی |
| ورود B موجود | Magic Link حاوی کد؛ بدون حساب جدید ناخواسته |
| کد اشتباه | عدم ورود، خطای امن و امکان اصلاح |
| کد تازه صحیح | نشست و فقط اطلاعات صاحب حساب |
| ارسال مجدد قبل/بعد از 60 ثانیه | قبل غیرفعال؛ بعد مجاز؛ استفاده از جدیدترین کد |
| گذشت 600 ثانیه | رد/غیرفعال‌شدن تأیید؛ نیاز به کد تازه |
| قطع شبکه یا 429 | پیام امن؛ دکمه‌ها گیر نکنند |
| reload | بازیابی نشست معتبر؛ نشست نامعتبر بدون داده |
| A/B مخفی | پروفایل دیگری در فهرست دیده نشود |
| انتشار B | A نام/معرفی را ببیند؛ بدون ایمیل یا یادداشت B |
| یادداشت متفاوت A/B | هرکدام فقط متن خود را ببیند |
| دنبال‌کردن/لغو A | شمارنده خصوصی هماهنگ؛ B فهرست A را نبیند |
| خروج و reload | پاک‌شدن ایمیل، یادداشت و فهرست از DOM و عدم بازگشت نشست |
| تعویض نقش A/B | دسترسی خصوصی متقابل رد شود |

پس از migration دو UUID جایگزین فایل 002 را با دو حساب آزمایشی تأییدشده همین پروژه عوض و کل فایل را یکجا اجرا کنید. نقش واقعی Postgres به authenticated/anon تغییر می‌کند؛ دستورات مورد آزمون با مجوز مدیر اجرا نمی‌شوند. خواندن/نوشتن خصوصی متقابل، جعل شناسه، تکرار/خوددنبال‌کردن، هدف مخفی و ناشناس آزموده می‌شوند. تغییر داده در پایان ROLLBACK می‌شود؛ پس از خطا نیز پیش از تلاش مجدد ROLLBACK کنید.

این آزمون امضای JWT و HTTP را نمی‌آزماید؛ پذیرش دو نشست واقعی نیز لازم است. متن PASS در فایل آماده، مدرک اجرای موفق نیست.

## نشست و هدرها

persistSession و autoRefreshToken فعال و نام ذخیره‌سازی مخصوص پروژه است. نشست بازیابی‌شده با getUser بررسی می‌شود؛ دیتابیس مرجع مجوز است. خروج scope:local دارد و دستگاه دیگر را خارج نمی‌کند. access token ممکن است تا انقضای JWT معتبر بماند؛ خروج هر کپی توکن یا داده قبلاً خوانده‌شده را فوراً باطل نمی‌کند.

localStorage به XSS حساس است. اسکریپت شخص ثالث نداریم، متن کاربر با textContent و اتصال CSP فقط همین Supabase است. SDK ثابت از رجیستری رسمی با SHA512 تطبیق و SHA256 ثبت شده است.

_headers پس از انتشار در Cloudflare Pages اعمال می‌شود؛ سرور محلی همه هدرها را شبیه‌سازی نمی‌کند. CSP متای HTML فعال است؛ frame-ancestors فقط از هدر HTTP عمل می‌کند. GitHub Pages فایل _headers را به‌عنوان تنظیم هدر اجرا نمی‌کند. این تحویل ممیزی جامع امنیت یا اثبات آمادگی برای داده حساس نیست.

## انتشار و برگشت

SQL و قالب‌های ایمیل فقط در پروژهٔ مجاز اجرا شدند. کاربر ثبت و ارسال فقط ۲۳ فایل جدید این قابلیت روی main را تأیید کرده است. DNS تغییر نمی‌کند. وضعیت واقعی انتشار باید در سامانهٔ میزبانی و روی دامنه بررسی شود. پس از انتشار، مسیر /auth-test/ و هدرهای HTTP روی دامنهٔ اصلی جداگانه بررسی شوند.

قبل از نصب دیتابیس، فقط فایل‌های جدید این تحویل را از نسخه انتشار بردارید. اگر بعداً _headers قواعد دیگری داشت، فقط بلوک /auth-test/* را بردارید.

بعد از نصب، ابتدا انتشار صفحه را متوقف و جدول‌های جدید را پشتیبان بگیرید؛ سپس rollback.sql را با تأیید جدا فقط در همین پروژه مرور و اجرا کنید. داده پروفایل/روابط این قابلیت حذف می‌شود؛ auth.users و SMTP حذف نمی‌شوند. CASCADE ندارد تا وابستگی جدید بی‌صدا حذف نشود. حذف حساب‌ها جزو rollback نیست.
